# Council review: gpt-6-astra (Codex CLI 0.158, `codex exec -m gpt-6-astra -s read-only`)

Reviewed the v0.3 draft of `docs/dev/DESIGN-v0.3-server-side.md` on 2026-09-28, read-only, no network. Brief: [`brief.md`](brief.md). Verbatim final answer:

## Verdict

**Revise before implementation.** The control-plane approach is sound, but the design overstates both trust verification and enforcement coverage. The most important change is a shared, mandatory verification stage that produces an immutable, fully authorized policy snapshot: `ConstraintStore.load()` alone does **not** establish that constraints are trusted. Reviewed read-only, without network access; confidence is high unless marked **(UNSURE)**, with current platform limits and cross-version behavior requiring confirmation.

## Findings

1. **[P0] Loaded constraints are not necessarily authorized or source-verified** — §§3.1, 5.1, 5.5 — `store.py` explicitly defers authority checking to the interceptor; file-source verification is skipped without a fetcher, and signatures are warning-only without a key. Compiling `store.constraints` directly can give unauthorized or unverified constraints enforceable cloud votes. **Fix:** extract a strict shared verification pipeline requiring signatures, source verification and authority checks before compilation or registration generation.

2. **[P0] Existing unresolved-scope paths bypass verification** — §§3.1, 7 — `interceptor.py` turns results from `get_env_unresolved()` and `get_time_window_unresolved()` into ESCALATE before checking their integrity or authority. An unauthorized loaded constraint can therefore deny admission when environment resolution fails. **Fix:** verify eligibility before every decision path, including unresolved conditions; add unauthorized and mutated-constraint cases to the adversarial corpus.

3. **[P0] Azure `NotActions` is not an enforceable deny** — §5.4 — `NotActions` subtracts permissions from that role’s `Actions`; another role assignment can still grant them. Merely attaching this role does not constrain existing Contributor/Owner permissions. The spec also omits the positive permission baseline from which to subtract. **Fix:** defer Azure deny compilation, or label this explicitly as least-privilege role generation requiring effective-role analysis and removal of overlapping grants.

4. **[P1] GCP needs a distinct deny-permission map** — §§5.3–5.4 — IAM deny supports a subset of permissions and uses deny-specific names such as `cloudresourcemanager.googleapis.com/projects.delete`, not the ordinary IAM spelling `resourcemanager.projects.delete`. A parser action map is insufficient. **Fix:** record supported deny permissions, canonical principal identifiers, attachment points and supported conditions per mapping; reject unsupported combinations. **(UNSURE: current supported-permission inventory and quotas.)**

5. **[P1] Azure platform description mixes several different controls** — §§5.2, 5.4 — Azure Policy `deny`/`denyAction` cannot generally select the requesting identity; `denyAction` currently concerns deletion. Those points are correct. But Azure-created deny assignments also include deployment-stack mechanisms, so “only managed applications and blueprints” is incomplete. `CanNotDelete` locks protect management-plane operations, not data-plane deletion, and sufficiently privileged identities can remove them. **Fix:** document these boundaries and keep optional global controls separate from identity-scoped output. **(UNSURE: current feature lifecycle and all denyAction exceptions.)**

6. **[P1] AWS evaluation claim needs explicit boundaries and size handling** — §5.4 — An applicable explicit Deny overrides Allow; that is correct. SCPs constrain member-account principals, do not grant permissions, exclude the management account and do not constrain service-linked roles. IAM role policies and SCPs are not interchangeable deployment artifacts. **Fix:** specify attachment hierarchy, principal matching, service-mediated calls and quota-aware output splitting. Account for the established 5,120-character SCP and 6,144-character managed-policy limits and attachment quotas. **(UNSURE: current quota changes.)**

7. **[P1] Cloud condition keys are not universally available** — §§5.2–5.4 — `aws:RequestedRegion` concerns the endpoint handling the request, not every geographic effect. Resource tags and resource-level ARN restrictions are action-dependent; unsupported or absent condition keys can make a Deny ineffective. **Fix:** make condition availability, required resource types, partition/account/region construction and missing-key behavior part of each action mapping; do not advertise unsupported combinations as exact.

8. **[P0] Replacing environment identity with tags weakens policy** — §5.2 — Current `environments.py` derives environment from operator-controlled account/project/context mappings. `env=prod` tags are a different predicate: missing or removable tags can let an action through that the CLI blocks. Merely reporting an assumed tag key does not repair this. **Fix:** compile the signed environment map into target scopes where possible; require protected tag governance and explicit missing-tag behavior for any tag-based approximation.

9. **[P1] Namespace deletion explanation is factually wrong** — §4.3 — Namespace-controller deletions do pass through API admission; the relevant problem is that their controller identity is excluded by this design. Also, the CLI already emits a synthetic namespace-cascade intent, so one namespace intent does not preserve current behavior. **Fix:** evaluate the initiating namespace deletion against child-resource restrictions using defined conservative cascade semantics; never depend on the example namespace rule being present.

10. **[P1] DeleteCollection guarantee remains too broad** — §§4.3, 10.1 — Generic Kubernetes storage performs per-object delete validation, but the spec needs to establish exactly what reaches external admission, especially names and `oldObject`, across supported versions and resource implementations. Aggregated APIs cannot simply inherit that guarantee. **Fix:** test raw collection deletes and controller-driven collection deletes; derive identity from validated request/object fields, and restrict the guarantee to tested API implementations. **(UNSURE: exact request-name behavior across every supported version.)**

11. **[P0] One intent per admission request loses security-relevant actions** — §4.3 — A single UPDATE can change replicas, images and other protected fields. Calling it only `scale` bypasses update/image restrictions; calling it only `update` misses scale restrictions. The CLI also uses `patch`, `set-image`, `cordon`, `rollout-*` and manifest resources, rather than this proposed canonical model. **Fix:** define shared semantic actions and derive multiple intents from object differences, combining verdicts with BLOCK precedence.

12. **[P1] `kind.kind` is not a reliable target identifier** — §4.3 — A scale request can carry kind `Scale`; exec can carry `PodExecOptions`; eviction targets a pod through an `Eviction` object. CREATE may use `generateName`, and DELETE has no new object. **Fix:** map group/resource/subresource plus operation and old/new objects through a versioned resource registry; handle conversion fields, CRDs, generated names and subresource-specific semantics explicitly.

13. **[P1] Admission coverage is narrower than “every path”** — §§1, 4.2–4.3 — Ordinary GET/LIST/WATCH are not admission operations. Exec/attach/port-forward use CONNECT admission, but existing sessions are not reevaluated. Eviction, ephemeral containers and proxy paths need separate treatment; access directly to a kubelet or data-plane endpoint is outside this webhook. Rules matching parent resources do not automatically cover their subresources. **Fix:** publish an endpoint/operation coverage matrix and generate explicit subresource rules.

14. **[P0] Controller delegation bypasses agent-only enforcement** — §§2–4 — An agent can create or modify an object that instructs an exempt operator, GitOps controller or cloud service to perform the blocked action. Deleting a parent can likewise cause exempt garbage-collector deletions. The control plane sees the delegate’s identity. **Fix:** constrain the initiating objects and delegation permissions, use dedicated constrained controller identities where feasible, and explicitly exclude unhandled transitive effects from the guarantee.

15. **[P0] Identity escape and enforcement tampering are unspecified** — §§3.2, 4.2, 5.4 — Agents may impersonate Kubernetes users, request other service-account tokens, launch workloads under privileged accounts, assume/pass cloud roles, mint service-account credentials, change identity tags or detach policies. Any such route defeats identity scoping. **Fix:** make prevention of identity switching and modification of enforcement configuration a deployment prerequisite, with concrete RBAC/IAM examples and negative tests.

16. **[P1] Namespace exclusions create bypasses** — §4.2 — Any matching agent action in an excluded namespace bypasses the webhook. Mutable namespace labels can also change selector behavior. Conversely, `namespaceSelector` does not exclude ordinary cluster-scoped resources such as Nodes; Namespace objects are selected using their own labels. **Fix:** prohibit agent writes in excluded namespaces using RBAC, protect selector inputs, and document cluster-scoped behavior precisely.

17. **[P1] Two identity lists and generated rules can silently diverge** — §§4.2, 4.5 — Adding an agent only to `agents.yaml` leaves it outside API-server matching; removing one there makes the handler allow it. Adding a protected resource to policy does nothing until registration rules also expand. Reloading the store is insufficient. **Fix:** version the identity configuration, registration and policy together, with safe rollout ordering and checks for active registration coverage.

18. **[P1] Last-good reload can preserve explicitly revoked rules indefinitely** — §§4.5–4.6 — An authority/key revocation or Git-source removal can fail the health threshold, leaving the old store enforcing rules no longer trusted. File/ref-change triggers also miss time-based expiry. This needs an explicit distinction between unavailable evidence and authenticated revocation. **Fix:** process revocations deliberately, bound stale operation, reload periodically, and define a separate unavailable-policy response rather than attributing denial to revoked constraints.

19. **[P1] Atomic reload needs a complete immutable snapshot** — §4.5 — Separate mounted files, signatures and a changing Git ref are not one atomic policy bundle. A fetch midway through verification can mix revisions; replicas may serve different generations. Fetching source history also does not ingest new rules into `constraints.yaml`. **Fix:** pin ref SHAs, verify one versioned bundle, recreate verification caches per generation, define ingestion/release mechanics and expose the active generation per replica. Track successful fetch time separately from commit timestamp.

20. **[P1] Admission protocol and failure semantics are incomplete** — §§4.1, 4.4, 4.6 — Kubernetes 1.30 GA `matchConditions` and `timeoutSeconds: 5` are correct; permitted webhook timeouts are 1–30 seconds. Responses must echo request UID and supply the proper AdmissionReview envelope; registration needs `admissionReviewVersions` and `sideEffects`. `failurePolicy` handles call failures, not explicit denials. **Fix:** specify the complete protocol, `sideEffects: None`, response limits and malformed-request handling. The outage-isolation claim holds only while identity filtering is correct.

21. **[P1] Dry-run and rate-limit semantics need separate contracts** — §§4.3, 7 — Allowing dry-run preserves today’s Aegis convention, but Kubernetes itself allows admission to deny dry-run; it is not a Kubernetes requirement. Meanwhile, admission acceptance does not prove execution: later validation can fail, and retries can repeat requests. The interceptor records ALLOW as executed, while no ledger means rate rules never fire. **Fix:** explicitly mark rate limits unsupported initially; test dry-run warning behavior without consuming quota or mutating enforcement state.

22. **[P1] Dependency avoidance is not a sufficient server design** — §4.1 — A thread pool does not bound accepted sockets, request bodies, slow clients or queued work. Two replicas and a PDB do not guarantee availability during node loss or correlated failure. Compromise also exposes a MAC verification key that can sign policy. **Fix:** specify bounded concurrency/body sizes/deadlines, network isolation, topology spread, resource limits, certificate rotation and hardened containers. Isolate the fetch sidecar and its credentials; prefer public-key-only verification before broad deployment.

23. **[P1] The compiler needs semantic validation beyond action triples** — §§5.2–5.3 — Constraints can use arbitrary parameter scopes, list alternatives, glob character classes and wildcard actions. Native permission names, condition languages and resource patterns do not preserve all of those semantics. Cloud parsers also have fallback forms, so their resource universe is not a closed finite table. **Fix:** validate every predicate, expand wildcards against a pinned supported universe, and distinguish exact, overblocking and underblocking translations. Never silently drop a predicate.

24. **[P1] Time-window claim overgeneralizes Azure** — §5.2 — AWS date conditions use absolute timestamps; they do not directly encode recurring weekday/hour schedules. GCP deny conditions support resource-tag functions, not arbitrary IAM-Allow time expressions. Azure RBAC `NotActions` supplies no time condition at all; “Azure conditions compare against absolute times only” conflates different products. **Fix:** document time support per emitted policy mechanism and report recurrence as unsupported. Do not ship attach/detach scheduling as equivalent enforcement.

25. **[P1] Drift claims exceed what the design observes** — §§5.1, 5.5–5.6 — Regeneration checks committed files, not deployed policies, attachments, selectors or bypass settings. `constraints_sha256` hashes only `constraints.yaml`; authority, signers, environment mappings and source revisions can change behavior without changing it. **Fix:** hash all effective inputs and compiler mappings, include output digests and attachment intent, and accept an operator-supplied deployment inventory for actual drift comparison.

26. **[P1] Self-written evaluators cannot establish cloud parity** — §7 — The compiler and its evaluator can share the same mistaken IAM semantics. Literal verdict parity also contradicts intentional ESCALATE→Deny translation, unsupported constructs and different dry-run behavior. **Fix:** define parity as equivalent enforcement for the declared exact subset; test approximations separately. Require target-service validation and real sandbox acceptance tests before calling a mapping exact, while documenting simulator limitations.

27. **[P1] Terraform and GitHub controls need their own trust boundary** — §6 — A required check is bypassable if an agent can edit its workflow, forge its result or apply a different plan. Rulesets generally govern matching refs across actors; they do not automatically implement the stated agents-only scope. Bypass actors and enforcement mode materially change protection. **Fix:** use protected verifier workflows and policy roots, bind approval to the exact saved plan and commit, restrict apply credentials, pin the expected check producer, and document ruleset scope and bypasses. **(UNSURE: current GitHub plan/feature availability.)**

28. **[P2] Phasing postpones essential controls and front-loads packaging** — §9 — Drift checking cannot wait until v0.4 if compilation ships in v0.3.x. Kubernetes coverage reporting is also needed immediately, despite being described mainly for compiled targets. **Fix:** first ship the strict trust snapshot and canonical intent contract; then a narrow webhook with coverage and adversarial integration tests. Move the Terraform example earlier, ship AWS verification/coverage/drift together, and defer Azure, scheduling and broad multi-cloud promises.

## Open questions (§10)

1. **DeleteCollection:** Treat per-object validation as the expected generic-storage behavior, not a universal guarantee. Gate supported versions/resources on integration tests, including request names, `oldObject`, namespace cleanup and partial failure.

2. **ESCALATE:** Deny. Allow-with-warning makes the server-side escalation requirement unenforceable; a human retry should carry an auditable link to the denied request.

3. **Time windows:** Report unsupported; defer the scheduler. Attach/detach races, propagation delays and scheduler failure can leave the wrong enforcement state active.

4. **Azure:** Defer the deny compiler. A separately named least-privilege role generator may be useful, but `NotActions` must never be represented as a deny guarantee.

5. **`agents.yaml`:** Operator-controlled, signed configuration outside agent-editable policy content. Generate CEL from that same versioned source; Kubernetes groups are authenticated identity attributes, not a substitute for trusted scope configuration.

6. **Minimum Kubernetes:** Require 1.30 or newer for this design, plus a tested maintained-version matrix. In-handler-only filtering makes webhook outages affect matching human/controller requests before the handler can exempt them.

## Missing from the spec

- A precise threat model covering delegated actions, identity switching and control-plane administrators.
- A complete request-to-intent and native-permission capability registry.
- Coverage categories for rejected constraints, unsupported predicates and directional approximations.
- Signed policy-bundle lifecycle: ingestion, revocation, rollback, expiry and empty-policy handling.
- Deployment attestation covering actual policy attachments and webhook registration.
- Break-glass ownership, audit requirements and recovery from webhook failure.
- Tests for bypass attempts, mixed-field updates, cascades, subresources, reload races and cloud condition absence.
- Explicit boundaries for data-plane operations and for Git releases beyond branch rulesets.
