# Council review: Claude Fable 5.1

Reviewed the v0.3 draft of `docs/dev/DESIGN-v0.3-server-side.md` on 2026-09-28, read-only, with
web access to official docs. Brief: [`brief.md`](brief.md). Verbatim final answer:

## Verdict

**Revise before implementing.** The architecture (identity-scoped server-side backstop + verified-subset compiler + coverage report) is right and matches Aegis's trust model, and most platform claims check out. But the spec has one trust-boundary hole that undoes the whole point: every server-side artifact it produces can be removed or evaded by the very identity it constrains, and the spec never says so. The single most important change: add a mandatory **self-protection layer** to every target — the compiled AWS/GCP/Azure policy must deny the agent identity the permissions to modify/detach that policy, mint new identities, or impersonate; the Kubernetes deployment must stop excluding the Aegis namespace from admission and must (via RBAC guidance + example rules) block agent writes to `ValidatingWebhookConfiguration`, RBAC, `serviceaccounts/token`, impersonation and the policy ConfigMap/Secret — and, because the in-cluster signing key is a *shared MAC secret* (PLAN §8), v0.2 step 2 (public-key signatures) should land before the webhook ships, or the key in the cluster becomes a signing oracle. Second: the compiler must re-run the **authority check** itself — `ConstraintStore.load` does not check authority (it is done in `AegisInterceptor.intercept`), so "loaded constraints only" would compile unauthorized rules.

## Findings

1. **[P0] The compiler's "loaded = trusted" premise is false: authority is not checked at load** — §3.1, §5.1, §5.5. `ConstraintStore.load` (store.py:948-1026) quarantines only `invalid`/`tampered`/source failures; `is_authorized` runs in `AegisInterceptor.intercept` (interceptor.py:199) at decision time, never at load. `aegis compile` taking `store.constraints` would emit Deny statements for a constraint whose principal is *not* authorized for its class — an `unauthorized` rule getting a vote, the exact case Aegis's benchmark separates on. Fix: define a `store.verified_constraints()` (or a compile-time pass) that re-runs `verify_integrity()` + `is_authorized()` per constraint and reports `unauthorized`/`tampered` in `coverage.json` as excluded-with-reason; the adversarial test in §7 must include an unauthorized-but-loaded rule and assert it is absent from every output.

2. **[P0] Compiled cloud policies are removable by the identity they bind** — §5.4 AWS/GCP/Azure. An identity-attached IAM Deny is undone by `iam:DetachRolePolicy`/`iam:DeleteRolePolicy`/`iam:CreatePolicyVersion`+`SetDefaultPolicyVersion` on itself, or side-stepped by `sts:AssumeRole` into another role, `iam:PassRole` to a service (Lambda/EC2/CloudFormation) that then does the delete, or `iam:CreateRole`. GCP: `iam.denypolicies.update/delete`, `iam.serviceAccounts.getAccessToken`/`actAs`, `serviceAccountKeys.create`, `resourcemanager.projects.setIamPolicy`. Azure: `Microsoft.Authorization/roleAssignments/write`, `roleDefinitions/write`, `locks/delete`, `policyExemptions/write`. Fix: every compiled output includes a non-optional **self-protection statement block** denying the agent identity these actions on itself, the compiled policy ARN/id, and identity creation/impersonation; the coverage report lists it; document that SCP (AWS) / org-level deny policy (GCP) is the only variant an account-level principal cannot remove, so recommend it as the default where an Organization exists.

3. **[P0] Kubernetes: excluding the webhook's own namespace, plus in-cluster key material, gives the agent a path to rewrite policy** — §4.2, §4.5. With `namespaceSelector` excluding the Aegis namespace, an agent with RBAC there edits the policy ConfigMap, and the signing Secret is a shared BLAKE2b MAC key (whoever can read it can sign, PLAN §8) — so it re-signs and the webhook reloads a rewritten policy unreviewed. Also unprotected by construction: the `ValidatingWebhookConfiguration` (cluster-scoped, agent can delete it or set `failurePolicy: Ignore`), `(Cluster)RoleBindings` (add self to a non-agent group), `serviceaccounts/token` CREATE and `kubectl create token` (mint a non-agent identity), `certificatesigningrequests/approval`, and creating a Pod/Job with a privileged `serviceAccountName` that does the delete under a non-agent SA. Fix: (a) drop the own-namespace exclusion — with identity `matchConditions` there is no self-deadlock (the Deployment/ReplicaSet controllers are not agents), so only `kube-system` needs excluding, and even that only by convention; (b) ship "guardrail rules" in the example policy: BLOCK agent CREATE/UPDATE/DELETE on `validatingwebhookconfiguration/*`, `mutatingwebhookconfiguration/*`, `clusterrolebinding/*`, `rolebinding/*`, `serviceaccount/*` (+ `token` subresource), `certificatesigningrequest/*`, and ESCALATE CREATE of pods/jobs whose `spec.serviceAccountName` is not the agent's own; (c) sequence v0.2 step 2 (public-key signing: webhook holds only verify keys) before v0.3.0, or at minimum mount the key read-only in a namespace with a documented RBAC deny for agents.

4. **[P0] Impersonation bypasses identity scoping on both layers** — §4.2. `kubectl --as admin` (or `--as-group`) makes `request.userInfo` the impersonated human; the kubectl parser *discards* `--as`/`--as-group`/`--as-uid` (`_DISCARD_VALUE_FLAGS`, parser.py:195-218) so the client hook sees an ordinary command and the webhook never receives it. Fix: parser marks `--as*` as `params["impersonate"]=True` → ESCALATE (like `unknown_target`); docs: agent RBAC must never include `impersonate`; impersonation is resolved before admission, so only RBAC stops it — say so.

5. **[P1] `matchConditions` example does not work for ServiceAccounts** — §4.2. `request.userInfo.groups.exists(g, g == 'aegis:agents')` requires a custom group; SA tokens carry only `system:serviceaccounts`, `system:serviceaccounts:<ns>`, `system:authenticated`. Custom groups exist only for OIDC/x509 users. Fix: scope by `request.userInfo.username in [...]` generated from `agents.yaml`, or by a dedicated namespace (`'system:serviceaccounts:aegis-agents' in request.userInfo.groups`) and document that pattern; guard with `has(request.userInfo.groups)` — a CEL error on a missing field with `failurePolicy: Fail` rejects the request for **everyone** matched by `rules` (verified: kubernetes.io/docs/reference/kubernetes-api/extend-resources/validating-webhook-configuration-v1/ — "If any matchCondition evaluates to an error… failurePolicy=Fail, reject the request").

6. **[P1] `failurePolicy: Fail` on clusters < 1.30 blocks everyone, contradicting §4.6** — §4.2 last paragraph vs §4.6. Without `matchConditions`, every request matching `rules` goes to the webhook, so an outage denies human and controller writes too. `matchConditions` is beta-on-by-default from 1.28 and GA in 1.30 (verified: KEP-3716, kubernetes/enhancements#3716; feature gate GA in 1.30). Fix: require 1.30 (see Q6); if older is supported at all, the manifests must set `failurePolicy: Ignore` and the docs must call that a different, weaker product.

7. **[P1] Fail-open mismatch between the two identity layers** — §4.2 (2). "A request from a non-agent identity is allowed with an audit annotation" means that when `agents.yaml` and the webhook registration disagree, the API server-flagged agent gets ALLOW. Fix: generate `matchConditions` from `agents.yaml` (`aegis webhook manifests`) so there is one source; treat "reached Aegis but not in `agents.yaml`" as deny + alert (the API server already asserted it is an agent). Keep allow-with-annotation only for an explicit `--unknown-identity=allow` operator flag.

8. **[P1] Intent mapping table has concrete errors** — §4.3. (a) `kind.kind` is wrong for subresources: `scale` requests carry `kind: autoscaling/v1 Scale`, `pods/exec` carries `PodExecOptions`, `pods/eviction` carries `Eviction`; use `request.resource.resource` (plural → parser's `_RESOURCE_ALIASES` singular) + `request.name`. (b) CREATE with `generateName` has empty `name` → resource must be `<kind>/*` (matches parser semantics), not `<kind>/`. (c) `pods/eviction` CREATE (what `kubectl drain` actually does) must map to `delete pod/<name>`, else the example `no-delete-in-prod-namespace` is bypassed by `kubectl drain`/eviction API. (d) PATCH arrives as `UPDATE`; `kubectl rollout restart` → CLI intent `rollout-restart` but webhook sees `update deployment/x` — either the webhook derives sub-actions from the diff (restartedAt annotation, image change → `set-image`) or the parity corpus documents them as CLI-only. (e) `status` subresource updates should map to `update` with `params.subresource` or be excluded from `rules`. (f) Namespace DELETE: the parser also emits a synthetic `*/*` delete scoped `namespace: <ns>` (parser.py:592-611); the webhook must emit the same second intent or `no-delete-in-prod-namespace` decides differently in the two layers, breaking §3.5. Note (UNSURE): for `namespaces/<name>` requests the API server sets `request.namespace` to the namespace's own name; do not rely on it — derive from `name` when `resource == namespaces`.

9. **[P1] Namespace deletion statement is factually wrong (conclusion still right)** — §4.3. The objects inside a deleted namespace are removed by the namespace lifecycle controller *through the API server*, so admission **does** run for them — under `system:serviceaccount:kube-system:namespace-controller`, which identity scoping excludes. Fix wording; also note it means a `kube-system` `namespaceSelector` exclusion is irrelevant here.

10. **[P1] `deletecollection` is per-item admission, but partial deletes happen** — §4.3, Q1. The generic registry implements DeleteCollection by listing and calling Delete per item with the user's identity, invoking admission per item (`operation: DELETE`, `name` set) — high confidence from apiserver source, not found stated in docs (UNSURE at the documentation level; verify on kind as the spec says). Consequence not in the spec: a mixed collection (some items denied) is **partially deleted** and the client gets an aggregated error. Coverage report and docs must say a webhook cannot make `kubectl delete pods --all` atomic.

11. **[P1] `exec` parity is broken today** — §4.3/§7. `kubectl exec api-0 -- sh` parses to resource `api-0` (bare pod name, `_LITERAL_RESOURCE_VERBS`, parser.py:558-561), while the webhook would produce `pod/api-0`. A rule written for either form misses the other layer. Fix the parser to emit `pod/<name>` (breaking change, needs a note in constraints docs) before building the corpus. Also list `pods/proxy`, `nodes/proxy`, `services/proxy` CONNECT subresources.

12. **[P1] `scope.env` compiled to a tag condition is fail-open, the opposite of the CLI** — §5.2. CLI: env-scoped rule + unresolved env ⇒ ESCALATE (interceptor.py:170-172). Compiled: `aws:ResourceTag/env = prod` ⇒ untagged resource is *allowed*. Fix: prefer **account/project/subscription → env** from `environments.yaml` (the compiler knows the target account at compile time, so `env: prod` rules compile *exactly* into the prod account's policy with no tag at all); tags only as a secondary mechanism, and then emit a second statement `"Null": {"aws:ResourceTag/env": "true"}` (deny when untagged) by default with `--untagged=allow` opt-out. Same for GCP (`resource.matchTag` absent ⇒ not denied). Report as `approximated` either way. (UNSURE: not every AWS action supports `aws:ResourceTag` — the action map must carry per-action condition-key support from the Service Authorization Reference, or the compiler emits an unconditional deny + `approximated`.)

13. **[P1] IAM `Sid` cannot hold rule ids** — §5.2 (ESCALATE row), §5.5. `Sid` allows only `[A-Za-z0-9]` and must be unique per policy (verified: docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_sid.html); `no-delete-nodes` is invalid. Fix: `Sid: Aegis<n>` + a `sid → rule id` map in the manifest; put `constraints_sha256` in the policy `Description`/tags, not in statements. Also size limits: managed policy 6,144 chars, SCP 5,120 (all characters count), 5 SCPs per target, 10 managed policies per role by default — the compiler must split/paginate output and the coverage report must say when it could not.

14. **[P1] GCP action map uses the wrong permission format** — §5.3. Deny policies require the v2 form `SERVICE_FQDN/RESOURCE.ACTION`, e.g. `cloudresourcemanager.googleapis.com/projects.delete`, `sqladmin.googleapis.com/instances.delete`, not `resourcemanager.projects.delete`; and only the permissions on the supported list may appear (docs.cloud.google.com/iam/docs/deny-permissions-support). The map YAML must carry the v2 name and a `deny_supported` flag; unsupported ⇒ `not expressible`. Correct in the spec: attachment at org/folder/project, `denialCondition` limited to `resource.matchTag`/`matchTagId`, deny evaluated before allow, `exceptionPrincipals`, 500 policies / 500 rules per resource (verified: docs.cloud.google.com/iam/docs/deny-overview).

15. **[P1] Azure `NotActions` is not a restriction unless it is the agent's only assignment** — §5.4. Microsoft: "`NotActions` is not a deny rule … if the user is assigned a second role that grants access to the same action, the user is allowed" (learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions). A managed identity in any group with Contributor is unconstrained. Fix: the Azure output must be paired with a `--check` that lists the identity's effective assignments (or the doc must require it), and the coverage report must say "action-level, non-additive, valid only while this is the sole assignment". Also missing: the newer **Deployment Stacks deny settings** (`denySettingsMode: denyDelete|denyWriteAndDelete`, `excludedPrincipals` up to 5 — use groups —, `excludedActions`, `applyToChildScopes`) create real deny assignments (learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deployment-stacks; deny-assignments page confirms stacks are the one user-reachable path). It is "deny all except humans" — the inverse of Aegis's identity scoping but a genuine control-plane deny for delete/write on stack-managed resources. Evaluate it before settling on `NotActions`. Correct in the spec: `denyAction` supports only `DELETE` and exempts locks/policy/deny assignments (learn.microsoft.com/en-us/azure/governance/policy/concepts/effect-deny-action); Azure Policy cannot scope by caller; users cannot create deny assignments directly; locks apply to everyone. Note Blueprints is being retired — drop it from the text.

16. **[P1] ESCALATE→Deny silently defeats the client-side "ask" flow** — §5.2, §4.4. With the compiled deny attached, an ESCALATE the human approved in Claude Code/Cursor still fails at the cloud; the approval was theatre. The webhook message covers this; the compiler doesn't. Fix: state it in §5.2 and in the hook's message for ESCALATE rules that are compiled (the hook can read `coverage.json`), and offer `--escalate=omit` for operators who want the ask flow to remain meaningful; default stays deny (safe).

17. **[P2] `time_window` claim needs nuance; the scheduler contradicts §2 non-goals** — §5.2, Q3. AWS: only `aws:CurrentTime`/`aws:EpochTime`, absolute (verified: reference_policies_condition-keys). GCP **allow**-policy IAM Conditions do support recurring windows (`request.time.getDayOfWeek(tz)`, `getHours(tz)`); deny policies do not. An attach/detach scheduler needs write credentials to IAM, which §5.1 says Aegis never holds. Recommend: `not expressible` + client-side; optionally document the GCP allow-side pattern.

18. **[P2] Drift check compares repo to repo, not repo to cloud** — §5.1, §5.6. "Committed output differs from regenerated" catches stale commits, not a policy someone detached or edited in the console. Fix: `aegis compile --check` optionally reads the live policy with read-only credentials (or consumes `terraform plan` JSON via the existing parser) and reports `deployed ≠ compiled`; embed `constraints_sha256` in the policy description/tag so the live object identifies itself.

19. **[P2] Reload semantics are underspecified** — §4.5. ConfigMap/Secret volume updates are eventual (kubelet sync + cache, ~1-2 min) and never propagate for `subPath` mounts; a reload half-way through a multi-file update (constraints.yaml new, `.sig` old) will fail signature → "keep last good" is right but must be tested; the Git sidecar needs a read-only deploy key and `--max-source-age` guidance. Also `load_cached` keys on `(path, mtime, size)` — fine for files, but the swap must be a whole-store atomic reference swap across worker threads.

20. **[P2] `http.server` is documented as not for production and has no request limits** — §4.1. Add a `Content-Length` cap (AdmissionReview carries `object`+`oldObject`; ~4 MiB is safe), read timeouts (slowloris), and either API-server client-cert auth (`--admission-control-config-file` kubeConfig) or a NetworkPolicy so only the API server can reach it; `/metrics` on a separate port.

21. **[P2] Per-request "cannot map" ⇒ deny is broader than the hook's rule** — §4.6. The hook denies only *infrastructure* commands it cannot parse; a webhook receives only what `rules` select, so deny is fine — but `rules` "generated from the policy" plus `operations: ["*"]` on `resources: ["*"]` in a permissive policy would deny every odd CRD write an agent makes. Say `rules` are generated from (provider=kubernetes) constraints' resource kinds only, and unmappable-but-selected ⇒ ESCALATE-as-deny with a distinct reason.

22. **[P2] Parity corpus needs equivalence classes, not "must agree on every case"** — §7. `kubectl apply -f x.yaml` → `manifest/x.yaml apply` (CLI) has no admission analogue; `scale` via UPDATE vs `kubectl scale`; `drain` vs eviction; namespace cascade. Define for each case: (a) identical intent, (b) CLI-only, (c) webhook-only, and assert agreement only within (a); also fix the case-sensitivity gap (`evade-case-variant` xfail in PLAN §8) before the corpus, since `Kind` case is normalised only on the CLI side.

23. **[P2] GitHub rulesets already have identity scoping — use it** — §6. Rulesets support `bypass_actors` (roles, teams, GitHub Apps) (docs.github.com …/available-rules-for-rulesets); Aegis should emit "block force push / restrict deletions / restrict updates / require status check" with bypass for the human teams — i.e. the same "deny everyone except humans" shape as Azure deployment stacks. Also `git` provider rules with `scope.repo`/`env` map cleanly to ruleset `conditions.ref_name` + repo targeting at org level.

24. **[P2] AWS SCP notes to add** — §5.4. SCPs also do not restrict service-linked roles (verified: orgs_manage_policies_scps); `aws:PrincipalArn` resolves to the role ARN, not the session ARN — good for scoping, but say so; `aws:RequestedRegion` for global services is `us-east-1`; RCPs are irrelevant here and should not be confused with SCPs.

25. **[P3] Audit annotation key is prefixed by the API server** — §4.4. Keys become `<webhook-name>/<key>`, and appear only at `Metadata`+ audit level; `warnings` >256 chars are truncated (verified from the admission docs). Document the exact key.

26. **[P3] Terraform gate is bypassable outside CI** — §6. If the agent holds apply credentials locally, the "server side" is really "credentials live only in CI". Say it, and pair with an SCP/deny that stops the agent's own identity from doing what the plan gate blocks.

## Open questions (§10)

1. **Yes, per item, `operation: DELETE`, with the caller's identity** (high confidence from apiserver `registry.Store.DeleteCollection`, not stated in docs — keep the kind test). Add: partial deletes happen; a collection delete is not atomic.
2. **Deny**, as drafted. Allow-with-warning makes an unverified/ambiguous state an ALLOW, which is the one thing Aegis's trust model forbids; kubectl warnings are stderr the model may not see.
3. **Report as not expressible; do not ship the scheduler.** It needs standing IAM write credentials (contradicts §5.1) and a missed detach silently widens permissions; GCP allow-side conditions are the only native recurring-time control and belong in a doc, not in v0.3.
4. **Do not ship `NotActions` alone.** It is non-additive and false comfort; evaluate Deployment Stacks deny settings (real deny assignments, group exclusions) and ship Azure only with that or with the broker. Locks for named resources are fine as an "everyone" control if the report says so.
5. **Policy directory, signed, operator-held (like `signers.yaml`), and generate the webhook `matchConditions` from it.** RBAC groups are agent-influenceable if RBAC is misconfigured, and SAs cannot carry custom groups anyway.
6. **Require 1.30.** Below it the failure mode is a cluster-wide write outage (finding 6); 1.28/1.29 have it beta-on-by-default if someone insists, but do not promise it.

## Missing from the spec

- Self-protection of the controls themselves (findings 2-4): agent RBAC minimums, IAM/GCP/Azure "don't let the agent touch the policy" statements, impersonation, token minting, `iam:PassRole`/`actAs`.
- Ordering dependency on v0.2 step 2 (public-key signing) so the in-cluster verifier never holds a signing-capable key; and a key-rotation/reload story for the webhook.
- Who may run `aegis compile` and how its output is signed/reviewed — the compiled artifact is now the effective policy; drift between reviewed output and applied output is the new attack surface.
- Multi-identity/multi-account matrix: one policy, N agent roles across M accounts/projects/clusters; how `environments.yaml` selects which rules go to which target (this is also the clean answer to `scope.env`).
- Webhook `rules` generation algorithm and its coverage report (which Kubernetes kinds/subresources are watched; `pods/eviction`, `*/scale`, CONNECT subresources).
- Latency/availability budget: store reload time with Git sources (PLAN §4: ~1.2 s at 10k rules with sources) vs the 5 s timeout during a rolling restart; PDB + `minReadySeconds`.
- Rate-limit ledger in the webhook (shared SQLite across replicas does not work; either drop `rate_limit` rules server-side with a coverage note, or specify a shared ledger).
- `--now`/timezone source for `time_window` rules inside the webhook (container TZ, tzdata presence — store.py already fails closed on missing tzdata; say the image ships tzdata).
- Observability: decision log destination/retention, request UID correlation with the API audit log, alerting on `reload_failures` and on `Fail`-policy denials caused by outage rather than policy.
- Explicit list of Kubernetes actions that exist only client-side (`apply`, `rollout-*`, `set-image`, `label`, `annotate`, `cordon`, `drain`, `taint`) and how a policy author should write rules that hold on both layers (e.g. write `update` + `delete` rules, not verb-specific ones).
- Threat table (like DESIGN-v0.2 §6) for v0.3: what each component stops, what it does not, and what remains for the broker.
