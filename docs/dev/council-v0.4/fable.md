# Council review: Claude Fable 5.1

Reviewed the v0.4 draft (revision 3) of `docs/dev/DESIGN-v0.4-public-key-signing.md` on
2026-09-29, read-only, with web access to official docs. Brief: [`brief.md`](brief.md). Verbatim
final answer:

## Verdict

**Revise before implementing.** The cryptographic core (SSHSIG, `find-principals` → `verify -I -n`, root-pinned `signers.yaml`, pin outside the policy tree, `workflow_run` split) is sound and the OpenSSH facts are mostly right. What is wrong is the *unit of trust*: the design signs raw file bytes with no binding to the file's role, path, policy set or version, so a validly signed file can be renamed, replayed from another deployment or an older commit, or simply **deleted** (`constraints.d/alice.yaml`, `plan_constraints.yaml`, `agents.yaml`) without any signature failing — and since every Aegis rule only restricts (`VALID_EFFECTS` = BLOCK/ESCALATE), deletion is the fail-open direction. The single most important change: sign a small canonical **envelope** (`kind`, `path`, `policy_id`, `serial`, `sha256(file)`) instead of bare bytes, and add a signed **policy index** listing the files that constitute the policy. That one change closes replay, cross-file confusion, silent removal, and gives Q4 its serial for free; everything else below is a fix to a section, not to the shape.

## Findings

1. **[P1] Signatures bind bytes, not role, path, set or version** — §4, §5.3, §5.4, §10 Q4 — The v2 signed message is the file's bytes in one namespace `aegis-policy`. A signature by alice on `constraints.d/alice.yaml` verifies equally as `constraints.yaml`, as `plan_constraints.yaml`, in another deployment that lists alice, or at any past version. Worse: removing a whole file is not a signature event at all — a merge that deletes `constraints.d/security.yaml` or `plan_constraints.yaml` (optional in `_resolve_config_paths`) removes rules with a green `aegis verify`. Fix: sign a canonical JSON envelope `{"v":2,"kind":"constraints|authority|signers|agents|environments|plan_constraints|repos|manifest|index","path":relpath,"policy_id":…,"serial":n,"sha256":…}`; store the envelope in `<file>.sig` beside the armored SSHSIG; add a signed `AEGIS-POLICY.index` (class `policy`, or root-signed) listing every file that makes up the policy, so absence is `missing-signed-file` and the set has one serial. Also use distinct namespaces for file vs manifest vs index (see #13).

2. **[P1] File-signing classes collide with rule classes** — §5.2 — `policy`, `identity`, `sources` are added to the same `principals:` lists as `deletion`, `scaling`, … and `constraint_class` is free-form (`validate_constraint_dict` in store.py only requires a non-empty string; `is_authorized` is a set lookup). Anyone holding `policy` (file class) can write rules with `constraint_class: policy` and they pass authority. `identity` already exists as a rule-visible class today. Fix: a separate `files:` section in `authority.yaml` (`files: {constraints: [alice], environments: [admin], …}`) or a reserved prefix (`file:policy`) that `validate_constraint_dict` refuses as a rule class.

3. **[P1] A v2 policy is only as strong as a v1 `signers.yaml`** — §5.1, §7 — The spec allows v1 and v2 to mix per file but never says that v2 *file* signatures must not be trusted while `signers.yaml` (or `authority.yaml`) is v1. If `signers.yaml` is MAC-signed, whoever holds the shared key (every verifier) adds a key and signs anything as anyone; the "verifier cannot forge" property is silently void. Fix: a v2 signature is accepted only when `signers.yaml` and `authority.yaml` are root-signed v2 against a configured pin; a v2 file under a v1 `signers.yaml` is `unverifiable-signer-list`, not "ok ssh alice".

4. **[P1] Hooks warn on shared-key: the gated agent usually *has* the shared key** — §6, §10 Q3 — The hook is the control that gates the coding agent; that agent runs as the operator and can read `$AEGIS_SIGNING_KEY`, `--key file:…`, or the example key `_resolve_key` (cli.py) falls back to. Under "warn", the agent rewrites `constraints.yaml`, MACs it with v1, and the hook accepts with a warning nobody sees (hook output goes to the model). Fix: strictness ratchets on a deployment-owned signal that already exists — **if any trust root is configured, v1 is refused everywhere** (`check`, hooks, `verify`) unless `--allow-shared-key`; with no trust root, v1 keeps working with the warning "shared-key mode: configure a trust root". No new flag to forget. Keep `compile`'s refusal.

5. **[P1] Threat model omits "the agent is the same OS user as the signer/pin owner"** — §8 — For local hooks, an agent running as the user can (a) use the user's `ssh-agent` (`SSH_AUTH_SOCK`) to `ssh-keygen -Y sign -n aegis-policy` as that user's principal, and (b) rewrite `~/.config/aegis-trust/trust-root`, mint a key and re-sign everything. `gitsource.py` already warns about (a); the spec's own line "whoever controls the operator's environment already controls what Aegis runs" concedes (b) but §8 has no row. Fix: add both rows; state that v0.4 protects *verifiers* (CI, Action, webhook) and *attribution*, and that local-hook protection requires sk-* keys with touch (or keys not on the dev machine) and a pin path the agent cannot write (e.g. `/etc/aegis-trust`, root-owned). Have `aegis check` warn when `SSH_AUTH_SOCK` is set and a listed key is loaded in it (`ssh-add -L` compare).

6. **[P1] File-source attribution under §5.3 is undefined** — §5.3, `provenance.py` — Two signers touch a file-sourced rule: the `constraints.yaml` signer (class `policy`) and the sources-manifest / `PRINCIPALS.yaml` signer (class `sources`). `verify_source_reason` still compares `PRINCIPALS.yaml`'s transport principal with `constraint.principal`, and the provenance hash includes `principal`. The spec says only that `PRINCIPALS.yaml` "can no longer attribute rules to someone other than the signer" — signer of *which* file? Fix: define it: the authenticated principal is the constraints-file signer; `PRINCIPALS.yaml` (if present) must agree or the rule is `principal-mismatch`; the `principal-from-payload` fallback is removed under v2; sources content is attested by the `sources` signer, attribution by the `policy` signer. Write it in §5.3 and the tests.

7. **[P2] `find-principals` does not check namespaces or crypto; say so and order the checks** — §5.4 — Correct in effect (verify runs after), but for the record: `sshsig_find_principals` passes `sig_namespace=NULL` to `check_allowed_keys_line`, so a key listed only with `namespaces="git"` still comes back from find-principals; the public key is *embedded in the SSHSIG blob* (attacker-chosen) and matched with `sshkey_equal`, so find-principals proves nothing until `verify -I <p> -n aegis-policy` succeeds. Also `verify -I` accepts any of that principal's keys, so the fingerprint you record must come from the signature's embedded key, not from signers.yaml. Output is one principal per line. Fix: the loader must build a *separate* allowed_signers for policy (`namespaces="aegis-policy…"`, never reuse the git one from `GitSourceFetcher`), treat find-principals output as a hint, and derive the fingerprint from the blob. Add the test "key listed with namespaces=git only must not verify a policy file".

8. **[P2] Version floor is wrong for the features used** — §3 — Right: sign/verify since 8.1 (2019-10-09), `find-principals` since 8.2 (2020-02-14). Wrong: `valid-after`/`valid-before` and `-Overify-time` arrived in **8.7** (2021-08-20); the `Z` UTC suffix in **9.1** (2022-10-04); a line with an unknown option is refused ("unknown key option", fail closed), so an 8.2 verifier rejects every expiring key. `-O print-pubkey` exists in current ssh-keygen; the release that added it I could not pin down (UNSURE) — do not depend on it. `ssh-keygen` has no `-V`; version must come from `ssh -V` (stderr) or feature probing. Floors in practice: RHEL 8 = 8.0 (cannot sign at all), Ubuntu 20.04 = 8.2, RHEL 9 = 8.7, ubuntu-22.04 runner = 8.9, 24.04 = 9.6. Fix: state "8.2 minimum; 8.7 for expiry; emit expiry as `YYYYMMDDHHMMSSZ` and require 9.1 when any key has `valid-*`"; parse the SSHSIG blob in Python (magic `SSHSIG`, uint32 version 1, pubkey string, namespace, reserved, hashalg sha256|sha512, signature — trivial) to get pubkey/namespace/fingerprint without `print-pubkey`.

9. **[P2] Pin by public key, not just fingerprint; and define root handling precisely** — §5.1, §5.4 — Verifying `signers.yaml` "against the pinned fingerprints only" needs the root's public key to build an allowed_signers; with fingerprint-only pins that key must be pulled out of the signature blob and hashed (fine, see #8, but the spec doesn't say). Simpler and safer: the trust-root file holds the full public key line(s) (optionally with `valid-*`), fingerprint printed for humans. Also: a pinned key that also appears in `signers.yaml` must be a load error (else Q5's "no" is unenforced); refuse `cert-authority` and `*-cert-v01@openssh.com` in both places (gitsource's `_SSH_KEY_RE` already excludes cert types — keep it); refuse a pin file that is a symlink into the policy tree.

10. **[P2] Revocation and rotation require the offline root every time** — §5.1, §8 — Removing a stolen key, rotating a laptop key, or renewing `valid-before` all mean a root ceremony; the root will end up online. Fix: (a) a deployment-owned revocation list passed as `ssh-keygen -Y verify -r` (KRL or one key per line; `gitsource` already plumbs an empty one via `gpg.ssh.revocationFile`) so a leak is killable without the root and without a merge; (b) allow `signers.yaml` to list `valid-*` per key and Aegis to emit them; (c) note the option of a root-signed `signers_admins:` delegation (two-tier) for v0.5.

11. **[P2] `policy` is too coarse for `environments.yaml` and `repos.yaml`** — §5.2 — A `configuration`-only developer who holds file class `policy` can re-sign `environments.yaml` so prod resolves as dev, defeating admin's prod-scoped `deletion` rules; a `sources` holder can repoint `repos.yaml` at a clone with rewritten history, resurrecting superseded (revoked) Git rules. Fix: classes `environments` and `repos` (or require the environments signer to hold every rule class used with an env scope, which is harder to explain).

12. **[P2] Snapshot/digest and reporting fields underspecified** — §6 — Include in the digest: per-input `(scheme, principal, fingerprint, serial)`, the trust-root fingerprints used, `require-public-key` mode, `--allow-example-keys`/`--allow-shared-key`, and the index serial. `aegis sources` and coverage reports need the new reasons `principal-unauthenticated`, `unverifiable-signer-list`, `missing-signed-file`, `file-class-unauthorized`. The Action's advisory/enforcing distinction should be a field in its output.

13. **[P3] Namespace naming** — §3 — OpenSSH recommends `name@your.domain` for custom namespaces; use `policy-file@aegis-devops.dev`, `policy-manifest@…`, `policy-index@…` (also separates manifest bytes from file bytes, see #1).

14. **[P3] sk-* / UP semantics** — §3 — `ssh-keygen`'s `sig_verify` logs but does not enforce the FIDO user-presence flag for sshsig (UNSURE whether `sshsig_verify` core rejects UP=0). Touch is enforced by the token at signing unless the key was made `no-touch-required`; say "hardware-backed" means non-exportable, and recommend keys generated *without* `no-touch-required`.

15. **[P3] Signing UX** — §6 — `ssh-keygen -Y sign -f` prompts for a passphrase on the TTY; through `subprocess` this hangs unless a TTY/agent is present. Prefer `-U`/agent by default, accept a bare `-----BEGIN SSH SIGNATURE-----` file produced by hand as well as the `aegis-sig-v2` form, and handle CRLF (fixed in 9.5). Also `constraints.d/`: define load order and cross-file duplicate-id handling (quarantine both).

16. **[P3] GitHub wording corrections** — §6.1 — Right: `pull_request` uses the merge-commit workflow file, no secrets and read-only `GITHUB_TOKEN` for forks; `workflow_run` runs only the default-branch definition; artifacts are untrusted (GitHub's hardening guide says exactly this); `pull_request_target` correctly avoided; name-matching of required checks is a real gap. Wrong/imprecise: approval-before-run is a setting for **public repositories' fork PRs** (any owner, with three tiers up to "all external contributors"), not "user-owned repositories"; required workflows are an **organization/enterprise ruleset** feature (private-repo availability plan-gated — UNSURE). Missing: `workflow_run.pull_requests` is empty for fork PRs, so the trusted job must resolve the PR by `workflow_run.head_sha` via the API and post the status on *that* SHA (not "the PR"), else a later push races the verdict.

## Open questions (§10)

1. **SSH now, optional pure-Python later — agree**, but freeze the allowed_signers subset Aegis emits (exact keys, `namespaces=`, `valid-*`, no patterns, no CA) so the later verifier can match `ssh-keygen` semantics exactly.
2. **Pinned root — agree**, with #9 (pin full key, root never in signers.yaml) and #10 (deployment-owned revocation list) so the root can actually stay offline.
3. **Disagree with "check/hooks warn"**: ratchet on trust-root presence (#4) — if a pin is configured, shared-key is refused everywhere unless `--allow-shared-key`; the hook warning is invisible to the human by construction.
4. **Don't just document**: put `serial` in the signed envelope/index now (#1) — cheap now, a v3 format later; enforce the high-water mark opt-in via a state file in the deployment-owned dir, and pin the snapshot digest in `compile`; the Action, having no state, checks the serial against the default branch's (`git show main:…`).
5. **Agree, no** — and enforce it: pinned key listed in `signers.yaml` is a load error; the root is never written into the policy allowed_signers.

## Missing from the spec

- Behaviour when v2 signatures exist but no trust root is configured (must be a hard error naming the pin locations, never a fallback to "unsigned" or v1).
- A signed policy index / handling of a missing optional file (`plan_constraints.yaml`, `agents.yaml`, `constraints.d/*`) — the fail-open direction (#1).
- File-source attribution and `PRINCIPALS.yaml` transition under §5.3 (#6); what `aegis sign` writes for `sources/` in v2.
- Threat rows: agent shares the OS user with signer/pin (#5); stolen `policy` key rewrites `environments.yaml` (#11); stolen `sources` key repoints `repos.yaml`.
- OpenSSH floors per feature and the parsing of the SSHSIG blob (#8); how the version is detected.
- Revocation without the root (KRL via `-r`) and key rotation for non-root principals (#10).
- Migration recipe for existing users: `aegis trust init` must also root-sign `authority.yaml`; `aegis sign --migrate` to re-sign a v1 tree; what happens to `signers.yaml` currently in `~/.config/aegis` (the config dir *is* a policy tree under the pin rule, so `~/.config/aegis-trust` must stay a sibling, never inside).
- Test plan additions: namespaces=git-only key rejected for policy; renamed/moved `.sig` rejected; deleted signed file detected; root key listed in signers.yaml refused; two pins with one expired; blob whose embedded key ≠ listed key; expired `valid-before` with and without `Z`; CRLF `.sig`; `constraints.d` duplicate ids; `workflow_run` template resolving a fork PR by `head_sha`.
- SECURITY.md / configuration.md / CHANGELOG updates and the Action repo (`moneytool/aegis-devops-action`, not in this tree) inputs (`trust-root`, `allow-shared-key`, advisory vs enforcing output).
