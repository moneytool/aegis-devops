# Council review: gpt-6-astra (Codex CLI 0.158, `codex exec -m gpt-6-astra -s read-only`)

Reviewed the v0.4 draft (revision 3) of `docs/dev/DESIGN-v0.4-public-key-signing.md` on 2026-09-29, read-only, no network. Brief: [`brief.md`](brief.md). Verbatim final answer:

## Verdict

**Revise before implementation.** SSHSIG, an externally pinned root, root-signed authority, and binding rules to authenticated signers are sound choices. The most important change is to define one deployment-owned verification policy that governs the entire load—including legacy fallback, manifests, required files, caches, and snapshots. Header-based dispatch alone does not preserve that boundary. Confidence is **high** in the findings below; implementation ambiguities are identified as such.

## Findings

1. **[P1] OpenSSH 8.2 is insufficient for the promised features** — §3, §9 — The stated dates for SSHSIG and `find-principals` are correct, but key-validity options and `-Oprint-pubkey` arrived in **8.7**. Subsequent releases fixed `find-principals` crashes and lifetime handling. Specify a tested minimum, preferably ≥8.9 with capability checks; unsupported features must fail closed. OpenSSH also becomes a new runtime requirement for users who currently use only file sources. [8.7 release notes](https://www.openssh.org/txt/release-8.7), [8.9 fixes](https://www.openssh.org/txt/release-8.9).

2. **[P1] Fingerprint-only root verification lacks an executable bootstrap procedure** — §5.1, §5.4 — `verify` needs public keys, not fingerprints, and the root need not appear in `signers.yaml`. Define how the embedded SSHSIG public key is obtained and matched to an external SHA256 pin before accepting either root-controlled file. One valid approach is successful `check-novalidate` over the exact bytes and namespace, followed by fingerprint comparison using its verified public key. Despite its name, it checks the cryptographic signature; it omits signer authorization. Never derive root trust from the unverified signer map. [OpenSSH implementation](https://raw.githubusercontent.com/openssh/openssh-portable/master/ssh-keygen.c).

3. **[P1] Signer discovery is correctly followed by verification, but the key schema is missing** — §3–§5 — `find-principals` discovers candidate identities; it does **not** prove that the file was signed. Step 3 correctly supplies that proof. However, existing `load_signers()` stores only key→principal and discards validity metadata. Define structured validity fields and generated lines such as `alice namespaces="aegis-policy",valid-before="…Z" ssh-ed25519 …`; keep Git’s namespace separate. Reject arbitrary options, wildcard principals and certificates/`cert-authority` for v0.4 unless certificate identity and revocation semantics are explicitly designed. Deduplicate decoded keys, not textual spellings. [Allowed-signers semantics](https://man.openbsd.org/ssh-keygen#ALLOWED_SIGNERS).

4. **[P1] Expiry is not equivalent to revocation, particularly for Git** — §3, §8 — SSHSIG has no authenticated signing timestamp. File verification should use deployment time, never a rule’s `source_timestamp`. Git deliberately validates key lifetimes at signature creation time; an attacker holding an expired key can backdate a new commit. Therefore “until … expires” overstates protection for Git-backed rules. Define current-time key eligibility separately, propagate it to both verification paths, and require removal/revocation for compromise recovery. Also define when long-running verifiers recheck expiry. [SSHSIG format](https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL.sshsig), [Git lifetime semantics](https://git-scm.com/docs/git-config#Documentation/git-config.txt-gpgsshallowedSignersFile).

5. **[P0] Existing demo-key discovery defeats the stated downgrade defense** — §6–§7 — `_resolve_key()` automatically reads `example-signing.key` beside the constraints file, accepting arbitrary hex there. Thus removing the deployment’s shared key does **not** remove MAC acceptance if this behavior survives migration: an attacker can supply their own key and MAC-signed policy. Remove policy-directory key discovery from operational verification. Require an explicitly configured legacy key and migration opt-in; a configured public-key root must never silently fall back to MAC trust for `signers.yaml` or `authority.yaml`. Define conflicts with `--insecure` and strictness settings as errors.

6. **[P0] Individually signed directory members do not authenticate policy completeness** — §5.3, §9 — A repository writer can delete a restrictive `constraints.d/alice.yaml` and its signature while leaving valid files behind. No forgery or old signature is needed. Existing optional-file discovery similarly permits disappearance of `plan_constraints.yaml` or `environments.yaml`. Require a signed inventory specifying required files, roles and digests, including explicit absence of optional components; fail the load on missing members. This is distinct from the acknowledged rollback gap.

7. **[P1] Manifest authorization and source attribution are underspecified** — §4, §5.2–§5.4 — The table classifies “the sources manifest” but omits detached source JSON and `PRINCIPALS.yaml`. It also does not define authorization when one manifest covers several file classes. A manifest’s `sources` permission must not authorize an embedded `authority.yaml` or constraints file. Define authorization per consumed member, root exceptions, signer attribution, and detached-versus-manifest precedence. Specify whether source-pack publishers may package other principals’ assertions; remove the existing payload-principal fallback where authenticated attribution is required. Bound manifest discovery and reject escaping paths and symlinks.

8. **[P1] Verification must consume the same bytes that loaders and snapshots use** — §5.4, §9 — Current loaders verify a pathname, reopen it for parsing, and sometimes reopen it again for hashing. A writable checkout can substitute unsigned bytes between those operations. Return immutable verified bytes plus evidence from the verifier; parse and hash that buffer. Load a coherent policy generation and publish it atomically. Merely replacing `check_signature()` with an SSH subprocess preserves this race.

9. **[P1] Existing caching can bypass a stricter verifier or revoked trust** — §9 — `ConstraintStore.load_cached()` keys only on pathname, mtime and size, explicitly ignoring key, authority and source-fetcher changes. Reusing that cache can return a legacy or insecure load during strict verification, or retain revoked authorization. Remove this cache from security-sensitive loads or bind entries to the complete trust context and verified content, with expiry/revocation invalidation.

10. **[P1] Plan constraints need explicit authentication and exclusion changes** — §5.3–§5.4, §9 — `PlanConstraintStore` currently has no source fetcher, so a `git:` string cannot justify the Git-signer exception. Implement actual Git verification there or require the file signer. Separately, `evaluate_plan()` evaluates quarantined and unauthorized predicates and can turn them into ESCALATE votes. Do not put `principal-unauthenticated` rules into that path. Exclude them entirely; any deployment-level rejection for degraded policy must be separate from an unverified rule’s predicate.

11. **[P1] Protecting workflow YAML does not isolate the apply gate** — §6.1(1) — Replanning and checking the exact saved plan is correct, but “nothing a PR edits reaches it” is false: merged Terraform configuration, providers, external programs and provisioners reach the pipeline. If they execute with apply credentials or can alter the verifier’s files/environment, they can bypass the check. Specify trusted executables and isolated planning/verifying/applying stages, immutable plan transfer, and the review boundary for executable Terraform dependencies. Pipeline-only credentials are necessary but insufficient.

12. **[P1] The `workflow_run` template is missing permissions and immutable run binding** — §6.1(2), §9 — Downloading another run’s artifacts needs `actions: read`, absent from the proposed permissions. Bind artifact retrieval to the triggering repository, workflow/run ID and attempt; bind policy checkout and reporting to the associated immutable PR SHA. Never use an artifact-supplied PR number or whatever HEAD is current later. Reject missing artifacts and stale/mismatched results. Install Aegis from a trusted pinned source, keep PR data outside executable/import paths, and avoid shared untrusted caches. [GitHub’s documented artifact workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

13. **[P2] GitHub check-spoofing mitigations need narrower claims** — §6.1(3) — The PR merge-workflow warning and default-branch `workflow_run` boundary are correct. Required checks can also be restricted to an expected GitHub App; choosing GitHub Actions still does not distinguish its workflows. Fork approval is useful manual review, not authentication, and does not cover every same-repository contributor. Ruleset workflows use a configured source/ref, not inherently every repository’s default branch. Document those limits and supported plans. Avoiding `pull_request_target` is reasonable, but `workflow_run` also has privileged-token risks. [Expected check sources](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [approval scope](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [workflow refs](https://docs.github.com/en/rest/orgs/rules).

14. **[P1] Rollback also restores revoked keys and authority** — §5.1, §8, §10 Q4 — The discussion focuses on old constraints, but replaying old root-signed `signers.yaml` can reauthorize a stolen key; replaying authority can restore removed privileges. Keeping two root pins is rotation overlap, not protection against a compromised pinned root. At minimum, support a deployment-owned accepted bundle digest and document emergency pin removal. A digest merely printed in a compiler manifest or existing Git history does not enforce freshness.

15. **[P2] One namespace does not bind signatures to file roles or deployments** — §3–§4 — `aegis-policy` correctly separates policy signatures from Git signatures, but detached signatures authenticate neither the destination filename nor policy domain; manifest mappings likewise lack deployment context. Valid signed material can be transplanted between deployments sharing keys. Sign a typed envelope containing format, role, policy-domain identifier and content digest, or explicitly define portability and enforce equivalent deployment scoping elsewhere. Use distinct detached/manifest domains.

16. **[P1] “Verifier holds only public keys” needs deployment and audit requirements** — §2, §6, §9 — Scrubbing the verification subprocess does not stop a compromised CI job from using an accessible SSH-agent socket or mounted private key. Require verifier deployments to have neither, preserving the v0.2 warning. Snapshots must record the authenticated root, effective strictness, legacy/demo overrides and transitive verification evidence—not just immediate file signers—so an SSH-signed file backed by MAC-authenticated trust cannot appear fully public-key verified.

## Open questions (§10)

1. **Use SSHSIG now.** It supports the intended key ecosystem; an optional Ed25519 backend must implement the same SSHSIG and authorization semantics, not merely verify raw Ed25519 signatures.
2. **Use externally pinned roots.** This avoids historical-chain availability and recovery complexity; specify bootstrap, rotation and compromise recovery first.
3. **Keep strict compile defaults; permit warning-only checks/hooks only for explicit legacy deployments.** New public-key initialization and the secretless Action should enable strict mode automatically.
4. **Defer automatic serial tracking, but add deployment digest pinning now.** Revocation rollback is too consequential to describe only as replaying old constraints.
5. **Do not authorize ordinary policy signing merely because a key is pinned.** Enforce this independently of authority-map membership; separate operational keys reduce root exposure.

## Missing from the spec

- A complete signer schema and supported algorithm matrix: Ed25519, both `sk-*` types, ECDSA and RSA; RSA SSHSIG uses SHA-2, not legacy RSA/SHA-1. [Protocol requirement](https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL.sshsig).
- Exact CLI recipes: agent signing still needs key selection; `--ssh-agent` alone is ambiguous. Strip the Aegis wrapper before invoking OpenSSH.
- Directory merge rules: duplicate IDs across authors, `default_tz` conflicts, plan-directory support, ordering and authenticated inventory ownership.
- End-to-end migration steps covering root-signed authority, new file permissions, multi-principal file splitting, source manifests, and removal of legacy fallback.
- Adversarial tests for deletion, cross-role manifests, wrong namespace, corrupt signatures that still yield principals, root mismatch, strictness conflicts, cache reuse, byte substitution, revoked-key rollback and stale workflow results.
- Real FIDO verification fixtures, RSA/ECDSA coverage and minimum-version CI. A FIDO-looking key-type string tests parsing, not signature verification.
- A clear demo bootstrap flow: public example roots must not become implicit deployment trust.
